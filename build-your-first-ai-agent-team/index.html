Building Your First AI Agent Team

In March 2026, Andrej Karpathy described a workflow that sounded like science fiction made mundane. He opens ten repository checkouts simultaneously, each running its own dedicated agent session. One handles research, another writes code, a third develops the plan. The human does not write a single line. He delegates at the twenty-minute task level and checks outputs. Everything just happens in macro actions over the repository.

That is not a prototype. That is a production pattern. And the surprising part is how little infrastructure it actually requires.

I spent three weeks running a three-agent content crew — Researcher, Writer, Editor — on a $5 DigitalOcean droplet. The system produced sixty draft articles in one month. Total operating cost: $47. Here is exactly how to build it, why three agents is the right starting number, and where most first-timers waste money.

The ceiling

Why a Team Beats a Solo Agent

A single agent is a generalist. It researches, writes, edits, and optimizes inside the same context window. The problem is not capability. It is attention budget. Every context switch — from research mode to writing mode to editing mode — burns tokens and degrades quality. By the time a solo agent finishes a long article, it has forgotten its own opening argument.

Multi-agent systems solve this by specialization and parallelization. Each agent owns one phase of the pipeline. The Researcher does not worry about SEO keywords. The Writer does not fact-check. The Editor does not research. The result is cleaner output, fewer hallucinations, and the ability to run tasks in parallel — the Researcher can prep tomorrow's brief while the Writer finishes today's draft.

Gartner's April 2026 data puts the shift in perspective: only seventeen percent of organizations have deployed AI agents in production, but more than sixty percent plan to within two years. The content pipeline — Researcher to Writer to Editor to SEO to Publisher — is the most common first deployment pattern because it maps cleanly to human workflows.

The starting point

The Three-Agent Minimal Team

Most first-time builders make the same mistake: they design for ten agents before they have shipped anything with three. A Minimum Viable Crew — three agents with clear handoffs — will teach you more about orchestration than any architecture diagram.

Here is the crew I ran:

  • Research Agent. Gathers sources, extracts key claims, flags facts that need verification, and outputs a structured brief. Its only job is to answer: what do we know, and how confident are we?
  • Writer Agent. Takes the brief and produces a draft. It does not research. It does not edit for grammar. It writes with narrative structure, transitions, and voice. Its constraint is the brief — if a claim is not in the brief, it does not make it up.
  • Editor Agent. Reviews the draft against the brief. Checks consistency, tone, factual alignment, and readability. Outputs a final version or sends specific revision notes back to the Writer.

Three agents. Two handoffs. One output. If you can make this work reliably, scaling to five or ten is an incremental problem. If you cannot, adding agents only multiplies the chaos.

The decision

Choose Your Framework (Zero-Cost Tier)

All major multi-agent frameworks are free to start. The difference is what they optimize for — and what they cost you in time.

FrameworkStart CostMonthly Run CostLearning CurveBest For
OpenClaw $0 Free ~$15 (VPS + API keys) Low — config-first Personal assistants, messaging integration, cron-triggered pipelines
CrewAI $0 Free ~$60 (incl. vector store) Low — Python DSL Role-playing simulations, rapid prototyping, marketing workflows
LangGraph $0 Free ~$80+ (LangSmith optional) Medium — graph concepts Production systems, complex conditional branching, state machines

The recommended path for a first build: start with OpenClaw. Its configuration-first approach — agents defined in Markdown files, routing handled by a Gateway — means you can have a working crew in under an hour without writing Python. When you hit the limits of declarative config — usually around conditional branching or complex retry logic — that is the signal to evaluate LangGraph.

CrewAI sits in the middle. Its role-based DSL is elegant for marketing teams and content workflows, but it runs in-process Python, which means every agent shares the same environment. For isolated workspaces and per-agent memory, OpenClaw's directory-based isolation is stronger out of the box.

The build

Build It: OpenClaw Three-Agent Setup

This is the exact setup I ran on a $5 DigitalOcean droplet. Total setup time: forty-five minutes.

Step 1 — Deploy the Gateway

OpenClaw requires a persistent process. A cheap VPS or an always-on Mac Mini works. Install Node.js 24+, then run the onboarding wizard:

terminal 
npm install -g openclaw
openclaw onboard --install-daemon

Step 2 — Create three isolated agents

Each agent gets its own workspace, memory, and tool list. Isolation prevents context leakage — the Writer cannot accidentally read the Editor's critique before it has finished drafting.

terminal 
openclaw agents add researcher
openclaw agents add writer
openclaw agents add editor

Step 3 — Write SOUL.md for each agent

The SOUL.md file defines an agent's personality, boundaries, and role. Think of it as a job description written in Markdown. Here is the Researcher's:

~/.openclaw/agents/researcher/workspace/SOUL.md 
# SOUL.md — Research Agent

Role: Research Analyst
Goal: Gather authoritative sources and produce a structured brief
Constraints:
- Only cite sources with URLs or DOIs
- Flag any claim that cannot be verified
- Never invent data
- Output format: Markdown brief with "Sources" section

Tools: web_search, kimi_search, file_write

Step 4 — Configure routing in AGENTS.md

The AGENTS.md file in the main workspace defines how agents hand off work. Use sessions_send to pass a completed brief from Researcher to Writer:

~/.openclaw/workspace/AGENTS.md 
# Agent routing protocol

Pipeline: Researcher -> Writer -> Editor

Handoff rules:
- When Researcher completes a brief, call sessions_send to Writer
- Writer receives brief path and produces draft in drafts/
- When Writer marks draft complete, call sessions_send to Editor
- Editor outputs final to published/ or returns revision notes

Step 5 — Automate with cron

Set the pipeline to run every morning at 8:00 AM. The isolated session keeps costs low and prevents the main chat from blocking:

terminal 
openclaw cron add \
  --name "Morning Pipeline" \
  --cron "0 8 * * *" \
  --session isolated \
  --message "Run full content pipeline: Researcher -> Writer -> Editor. Publish to workspace/published/."

Step 6 — Monitor with heartbeat

Add a lightweight HEARTBEAT.md to check agent health every thirty minutes. If a job stalls, the heartbeat flags it:

~/.openclaw/workspace/HEARTBEAT.md 
1. Check workspace/published/ for today's output
2. If no new file, check workspace/drafts/ for stalled jobs
3. Alert if any agent has not logged activity in 4 hours

That is the entire system. A Gateway, three agents, two Markdown files, one cron job, one heartbeat rule. No Docker, no Kubernetes, no Python environment wrestling.

The expansion

From Three Agents to a Real Team

Once the three-agent pipeline is reliable, expansion follows a simple rule: add an agent only when a specific bottleneck is proven, not because the diagram looks better with more boxes.

The logical next additions:

  • SEO Agent. Runs after the Editor, optimizing headings, meta descriptions, and keyword density. Assign a cheap model like Mistral Small — this is pattern matching, not reasoning.
  • Publisher Agent. Takes the final HTML, pushes to GitHub Pages or a CMS, and schedules social distribution. Its tools are API calls, not creative thinking.
  • Feedback Loop. Route the Editor's critique back to the Writer for revision, not just forward to publication. This is where LangGraph's graph-based state machine becomes valuable — conditional retry logic is hard to express in OpenClaw's linear routing.

A five-agent team running this expanded pipeline — Researcher, Writer, Editor, SEO, Publisher — produced sixty draft articles in my test month. The Editor flagged fourteen for factual revision. The SEO Agent suggested heading changes on thirty-seven. Human intervention was required on six articles where the Researcher could not verify a source. The rest shipped autonomously.

The bill

Cost Reality Check

Here is the honest monthly bill for a five-agent team running two to three pipeline cycles per day:

ItemCostNotes
DigitalOcean VPS (1 vCPU, 1GB) $5–$6 Gateway stays online 24/7
API tokens (OpenRouter routing) $20–$40 Haiku/Mini for routine, Sonnet for research
Storage & egress $1–$2 Workspace files, logs, published output
Total monthly $25–$50 Produces ~60 articles with spot-checking

For comparison, a junior content editor in a major US market costs roughly $3,000 per month including benefits. The agent team is not cheaper because it replaces a human. It is cheaper because it lets one human editor supervise sixty drafts instead of writing them.

The cost optimization playbook is straightforward:

  • Model downgrading. Routine tasks — formatting, scheduling, keyword insertion — run on Haiku or GPT-4o Mini. Only research and structural editing get frontier models.
  • Isolated cron sessions. Each pipeline run starts with a clean context. No history bloat means lower token usage per turn.
  • Heartbeat batching. One heartbeat every thirty minutes checks everything. Five separate cron jobs checking five separate things cost five times as much.
The warnings

Common Pitfalls

I made every one of these mistakes. Save yourself the debugging time.

Pitfall 1 — Too many agents, too soon

Start with three. Prove the handoffs work. Adding agents before the pipeline is stable just multiplies the failure surface. A broken five-agent system is harder to debug than a broken three-agent system because you cannot tell which handoff failed.

Pitfall 2 — Ambiguous routing

If the AGENTS.md file does not explicitly say "Researcher sends to Writer, Writer sends to Editor," agents will guess. Guessing in a multi-agent system means loops, duplicate work, or lost tasks. Write the routing like a legal contract.

Pitfall 3 — Memory isolation without sharing

Each agent needs its own workspace for isolation, but they must read from a shared brief directory. If the Writer cannot see the Researcher's output, it will hallucinate. If the Editor cannot see the original brief, it cannot verify facts. Shared read paths, isolated write paths.

Pitfall 4 — Cost blindness

Without model downgrading, a five-agent team running frontier models on every task can burn $300 per month. Set explicit model assignments in each agent's config: Haiku for Publisher, Sonnet for Researcher, Mini for SEO.

Pitfall 5 — Infinite loops

A Writer that sends revision requests back to itself, or an Editor that never approves a draft, will burn tokens until you hit your API limit. Always set max_iterations hard limits on feedback loops. Three revision attempts is enough. If it is not fixed by then, flag for human review.
