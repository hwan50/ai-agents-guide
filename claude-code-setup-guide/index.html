Starting point

What "vanilla" Claude Code actually gives you

Out of the box, Claude Code is a terminal-based chatbot that can read files and run shell commands. That's genuinely useful — I use it daily for refactoring, debugging, and exploring unfamiliar codebases. But it's also limited:

  • No persistent memory of your project's conventions
  • No access to external databases, APIs, or documentation
  • No way to delegate sub-tasks to specialized agents
  • No automation — you type everything manually

The "messy" feeling that tweet describes? It's real. You're essentially pair-programming with a very smart colleague who has goldfish memory and no access to your company's internal tools.

Here's how to fix that.

Component 01

Hooks: teaching Claude your workflow

Hooks are event triggers that run custom logic before or after Claude takes action. Think of them as Claude's nervous system — they let you intercept and modify behavior at specific moments.

What you can actually do with hooks

Here are three I use daily:

  • Pre-command validation. Before Claude runs rm -rf or git push --force, pause and ask for confirmation. I've caught accidental destructive commands twice this week.
  • Auto-format on save. When Claude writes a file, automatically run Prettier or Black. No more "can you format that?" back-and-forth.
  • Context injection. Before every response, prepend your team's coding standards. Claude suddenly knows you use 2-space indents, prefer early returns, and hate nested ternaries.

How to configure hooks

Claude Code uses a claude.md file in your project root for persistent instructions. For hooks, create a .claude/hooks/ directory:

project structure 
.claude/
├── hooks/
│   ├── before-command.sh    # Runs before any shell command
│   ├── after-write.py       # Runs after Claude writes a file
│   └── pre-response.md      # Injected into every context
└── claude.md                # Global project instructions

Example before-command.sh:

before-command.sh 
#!/bin/bash
# Safety gate for destructive commands
if [[ "$1" =~ ^rm\ -rf|git\ push\ --force|DROP\ TABLE ]]; then
    echo "⚠️  Destructive command detected: $1"
    echo "Type 'yes' to proceed:"
    read confirmation
    if [[ "$confirmation" != "yes" ]]; then
        exit 1
    fi
fi

Make it executable (chmod +x) and Claude will respect it. The integration isn't officially documented yet — this works because Claude Code reads .claude/ as a convention directory.

Component 02

Skills: giving Claude domain expertise

Skills are structured knowledge files that teach Claude how to work with specific technologies. Unlike the generic "I'm a helpful assistant" baseline, a skill tells Claude exactly how your team uses React, how your GraphQL schema is organized, or what your deployment pipeline expects.

Real example: a Next.js App Router skill

I wrote this after Claude suggested getServerSideProps in a Next.js 14 project. It kept happening until I gave it structured context:

.claude/skills/nextjs-app-router.md 
## Project Structure
- App directory: `/app`
- API routes: `/app/api/*`
- Server components: default in `/app`
- Client components: marked with `"use client"`
- Data fetching: Use Server Components with async/await

## Forbidden Patterns
❌ getServerSideProps, getStaticProps (pages router only)
❌ fetch in useEffect
❌ Direct database access from client components

## Required Patterns
✅ Server Components for data fetching
✅ Route handlers at `/app/api/[route]/route.ts`
✅ Suspense boundaries for async content

## File Naming
- Page component: `page.tsx`
- Layout: `layout.tsx`
- API route: `route.ts`
- Loading state: `loading.tsx`
- Error handling: `error.tsx`

After adding this, Claude stopped suggesting deprecated patterns. It even started proactively creating loading.tsx when I asked for new pages.

How skills differ from regular prompts

Regular prompt

  • One-shot, forgotten next session
  • Scattered across chat history
  • Claude interprets loosely
  • Generic advice

Skill file

  • Persistent, loaded automatically
  • Centralized, version-controlled
  • Structured, rules-based
  • Project-specific conventions
Component 03

MCP servers: connecting Claude to the outside world

MCP (Model Context Protocol) servers are the most powerful and least understood part of the Claude ecosystem. They let Claude talk to databases, APIs, browsers, and other tools through a standardized protocol.

What MCP actually does

Without MCP, Claude can only see what you paste into the chat. With MCP, Claude can:

  • Query your PostgreSQL database to check schema before writing migrations
  • Read your Notion docs to understand product requirements
  • Control a headless browser to test the UI it just built
  • Access your GitHub issues to prioritize bug fixes

I have a Postgres MCP server configured. When I ask Claude to "create a migration for the new user fields," it queries the current schema first, checks for conflicts, then generates the migration. It used to hallucinate column types; now it's accurate because it actually reads the database.

Setting up your first MCP server

Claude Code supports MCP through a configuration file. On macOS, it's at ~/Library/Application Support/Claude/claude_desktop_config.json:

claude_desktop_config.json 
{
  "mcpServers": {
    "postgres": {
      "command": "npx",
      "args": ["-y", "@anthropic/mcp-server-postgres", "postgresql://localhost/mydb"]
    },
    "github": {
      "command": "npx",
      "args": ["-y", "@anthropic/mcp-server-github", "--token", "YOUR_TOKEN"]
    },
    "filesystem": {
      "command": "npx",
      "args": ["-y", "@anthropic/mcp-server-filesystem", "/path/to/project"]
    }
  }
}
Important

MCP servers run as separate processes on your machine. They have the permissions you give them. The filesystem server can delete files. The Postgres server can drop tables. Configure carefully.

Community MCP servers worth trying

@anthropic/mcp-server-filesystem Read and write local files. Use for any project.
@anthropic/mcp-server-postgres Query PostgreSQL. Use for database work.
@anthropic/mcp-server-github Read issues and PRs, create branches. Use for GitHub workflow.
mcp-server-puppeteer Control a headless browser. Use for UI testing and scraping.
mcp-server-sqlite Local SQLite queries. Use for mobile and dev tools.
Component 04

Subagents: delegation without chaos

This is where it gets interesting. Claude can spawn specialized sub-agents for specific tasks — a code review agent, a testing agent, a documentation agent — and coordinate their work.

How I use subagents

My workflow for a new feature:

  1. I tell the main Claude: "Implement user authentication with JWT tokens."
  2. Claude spawns a Research Agent to check our existing auth patterns in the codebase.
  3. Research Agent reports back: "We use Passport.js with local strategy, JWT stored in httpOnly cookies."
  4. Claude spawns an Implementation Agent with the research context.
  5. Implementation Agent writes the code.
  6. Claude spawns a Review Agent to check for security issues.
  7. Review Agent flags: "JWT secret is hardcoded — should use env var."
  8. Claude fixes it and presents the final result.

This sounds futuristic, but it's achievable today with the right setup. The key insight: each subagent gets a narrow system prompt and specific tools. You don't spawn "another Claude" — you spawn a specialist with amnesia about everything except its job.

Configuration example

.claude/agents/review-agent.md 
You are a security-focused code reviewer.
You only look for:
- Hardcoded secrets
- SQL injection risks
- XSS vulnerabilities
- Insecure dependencies

Do not comment on style, performance, or architecture.
Return findings as a JSON array with "severity" and "fix" fields.

I invoke it with: /agent review-agent check src/auth.ts

Reality check

Full multi-agent orchestration like I described requires custom scripting. The /agent command and structured sub-agents are still emerging features. What's available today: you can run separate Claude Code instances with different claude.md configs, or use the API with different system prompts.

Component 05

Automations: removing repetitive work

Automations are triggered workflows that run without manual prompting. They turn Claude from reactive (you ask, it answers) to proactive (event happens, Claude acts).

Practical automations I actually use

Auto-commit messages. I have a git hook that sends my staged diff to Claude and asks for a conventional commit message. It runs git commit with an AI-generated message following the type(scope): description format.

.git/hooks/prepare-commit-msg 
#!/bin/bash
# .git/hooks/prepare-commit-msg
DIFF=$(git diff --cached)
MSG=$(claude --quiet "Write a conventional commit message for this diff:\n$DIFF")
echo "$MSG" > "$1"

Dependency update summaries. Weekly, a cron job runs npm outdated, pipes the output to Claude, and asks: "Which updates are safe to apply? Which need manual review?" Claude outputs a markdown table with risk assessment. I review it in 30 seconds instead of manually checking each package's changelog.

PR description generation. When I create a PR branch, a script asks Claude to summarize the commits, explain the motivation, and list testing steps. I edit lightly and submit. It saves about 5 minutes per PR.

The automation mindset

Every time you find yourself copy-pasting output from Claude, or asking the same sequence of questions, that's an automation candidate. The pattern is always:

  1. Collect context (git diff, file changes, test output).
  2. Send to Claude with a structured prompt.
  3. Capture the output.
  4. Put it where it belongs (commit message, PR description, Slack).
The full picture

Putting it all together: my setup

Here's what my Claude Code environment actually looks like in practice:

my-project/ 
my-project/
├── .claude/
│   ├── claude.md              # Global project context
│   ├── hooks/
│   │   ├── before-command.sh  # Safety gate
│   │   └── after-write.py     # Auto-format
│   ├── skills/
│   │   ├── nextjs.md          # Framework rules
│   │   ├── testing.md         # Test conventions
│   │   └── deployment.md      # Deploy checklist
│   └── agents/

│       └── test-agent.md      # Test generator
├── .github/

This took about two hours to set up initially. Now it saves me 15–30 minutes per coding session. The ROI was positive after the third day.

Honest status

What's actually available vs. what's coming

Not everything described here is equally mature. Here's an honest breakdown:

CapabilityStatusHow
Skills (claude.md) Stable Create .claude/skills/*.md
Hooks (safety gates) Experimental .claude/hooks/*.sh with conventions
MCP servers Released claude_desktop_config.json
Subagents Early Separate configs / API calls
Automations DIY Shell scripts + cron + Claude API
Project scanner Not yet The "claude-code-setup" plugin from the tweet

The tweet that started this mentioned a plugin that "scans your project and recommends setup." That specific tool doesn't exist as a single installable package yet. But you can approximate it by manually creating the structure described above. It's more work, but you understand what each piece does instead of blindly accepting defaults.

The verdict

Should you do this?

If you use Claude Code less than once a week, probably not. The setup overhead won't pay off.

If you use it daily, absolutely yes. The marginal cost of each interaction drops significantly when Claude knows your conventions, has access to your database schema, and follows your safety rules.

The messy feeling of "vanilla" Claude Code isn't a bug — it's the default state before configuration.

Every serious IDE requires setup: VS Code needs extensions, Vim needs .vimrc, Emacs needs... well, Emacs always needs something. Claude Code is no different.

The difference is that once configured, it knows your codebase better than any IDE extension because it can actually read, understand, and reason about the code — not just syntax-highlight it.
